# Security and privacy boundaries

Design baseline 2026-10-08. Educational public site, no patient data processing. These controls are proposed and must be verified in Prompt 2; no security audit of a running application has occurred.

## Threat model

Assets: integrity of educational content, provenance, source repository, build pipeline and static distribution. Relevant threats: compromised dependencies, malicious MDX/content contributions, script injection through search/URL state, mislicensed data inclusion, secrets accidentally emitted in static files, and visitors mistaking examples for clinical advice or validation. No authentication system or clinical database is in scope.

## Data minimization

No uploads, free-text submissions, comments, accounts, analytics SDKs, cookies, session replay, newsletter, or patient-entry forms. Search executes locally and uses URL fragments; do not transmit query text, collect search history, or store it in localStorage. Users can still share fragments themselves. Hosting providers may retain request/IP logs; privacy text must acknowledge this without inventing retention periods. Inspect actual provider settings before publication and document them. Third-party links disclose navigation to an external site.

## Content and input controls

MDX is executable content and is trusted repository code, not user input. Restrict authoring to reviewed local files, disallow raw HTML and arbitrary MDX imports/exports, register only approved components, and validate URLs. Do not fetch/compile remote MDX. Render search strings with React text escaping; no `dangerouslySetInnerHTML`, user regex, eval, or dynamic module paths. Limit queries to 120 characters, ignore unsupported hash parameters, and safely handle malformed percent encoding.

Only HTTPS external content links are allowed; reject javascript/data schemes in content. Prefer same-tab navigation; if a new tab is necessary, add `noopener noreferrer` and an accessible indication. Treat external pages as untrusted. No embedded remote scripts, images or tracking widgets.

## HTTP controls for static hosting

Configure at the chosen host and validate actual response headers; Next static export does not supply runtime header support ([Next documentation](https://nextjs.org/docs/app/guides/static-exports), accessed 2026-10-08).

- Content-Security-Policy baseline: `default-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'; connect-src 'self'; img-src 'self' data:; font-src 'self'; script-src 'self'` plus build-derived hashes for unavoidable inline Next scripts. No unsafe-eval. Scripts must not require broad unsafe-inline. Style inline exceptions, if generated by the framework, require a documented narrow decision and test.
- Generate hashes from final emitted HTML, per route if needed; hash policy and artifact must be released atomically. Nonces are inappropriate without a request server. Verify host header size/rule limits before choosing representation. If safe CSP cannot be delivered within provider limits, resolve architecture/header strategy before publication, not by silently dropping the policy.
- `X-Content-Type-Options: nosniff`; `Referrer-Policy: no-referrer`; `X-Frame-Options: DENY` as compatible defense; Permissions-Policy disables camera, microphone and geolocation.
- HSTS only after HTTPS and chosen domain are verified; do not includeSubDomains/preload blindly on an owner domain shared with unrelated services.
- HTML revalidation; immutable caching only for versioned/hashed assets. Correct MIME for JSON/CSV and download filenames.

## Dependencies, CI and secrets

Pin the lockfile; use a supported Node LTS and compatible stable package versions. Review direct and transitive license notices. Produce an inventory identifying packages, versions, license expressions and unresolved cases; unresolved distribution terms block release of that dependency. Recheck reported vulnerabilities for actual runtime/build exposure; no untriaged high/critical issue at release. Do not assume a scanner passing proves safety.

GitHub Actions should use minimum `contents: read`, pinned action commits, timeouts and unprivileged pull_request verification. Avoid `pull_request_target` with untrusted checkout. Production deploy credentials are absent from test workflows. No standards API keys are needed. Do not expose secrets in NEXT_PUBLIC variables, logs, generated indexes or examples. Never read employer credentials. Inspect release output for accidental source paths and secret patterns without printing possible secret values.

## Clinical and licensing controls

All fixtures are original synthetic records with explicit labels, fixed fictional IDs and documented limitations. No dictionary-coded data without separate rights and validation. Do not accept “de-identified” real records as synthetic. Rights gating covers HTML, downloads, indexes and cached build artifacts. Every reference claim is versioned and sourced; corrections are recorded in content release notes.

## Errors, accessibility and operations

404 and search failure pages provide recovery without stack traces or local paths. Keyboard and screen-reader checks are release requirements; automated checks are supplemented by manual verification. Dependencies and source references are reviewed during maintenance. After an integrity incident, remove affected content, roll back to a known reviewed artifact, rotate any exposed personal-project secret, and document corrective action. No claim of HIPAA, GDPR, GxP, FDA or CDISC certification is made. Privacy/legal obligations must be assessed against the actual deployed configuration; the architecture minimizes collection rather than promising universal compliance.
